# Restaurant Orders

Tablet ordering and kitchen ticket system, built first for the owner's family Chinese takeout
restaurant and meant to become a SaaS product sold to many restaurants (like Toast).

The problem: the cashier shouts orders to the kitchen and chefs must remember them, which breaks
down when it gets busy. The cashier enters orders on a tablet instead, and a kitchen ticket
prints so chefs can see which orders are open and which are done.

- `docs/api-plan.md` – the future backend's endpoints and server-side rules.

## Decisions

- **Native Android app first (Kotlin, `apps/android`), for the family restaurant only.** One
  tablet keeps its own data and sends tickets straight to the kitchen printer on the restaurant
  network, the way Square, Toast and ZBS do. No server, no App Store fees (the APK is installed
  directly).
- The kitchen printer is the restaurant's existing generic 80 mm ESC/POS printer (ZBS-branded).
  It takes raw bytes on TCP port 9100 and can't fetch tickets from the cloud.
- A backend comes when it's needed: a second device (kitchen screen), online orders, in-app card
  payments or more restaurants. `docs/api-plan.md` is its blueprint; the SaaS goal (many
  restaurants, roles, Postgres) still stands for later.
- Roadmap: v1 printed kitchen tickets; v2 kitchen screen and Ready status; v3 card payments
  (premium feature) and reports; later online orders, pickup screen, stations, bilingual tickets.
  The current register keeps handling payments until v3.
- The family restaurant tests every phase before any other restaurant sees it.

## Android app (`apps/android`)

Kotlin · Jetpack Compose · Room (SQLite) · coroutines · Gradle (Kotlin DSL, version catalog in
`gradle/libs.versions.toml`). See `apps/android/README.md`.
- `core/` – plain Kotlin, no Android SDK needed: `domain/` (types, pricing, modifiers, order
  lines, ticket layout, permissions, starter menu) ported from `apps/frontend/src/domain`, and
  `printing/` (ESC/POS bytes, network printer). Keep both apps' rules the same.
- `core/src/main/resources/starter-menu.json` is generated by
  `node apps/android/scripts/export-starter-menu.mjs` from `apps/server/src/menu-data.ts` and
  `apps/frontend/src/data/starter-modifiers.ts`. Re-run it after changing either.
- `app/` – the Android app: `data/` (Room database, repositories with the rules from
  `apps/frontend/src/data/mockApi.ts`), `printing/PrintQueue.kt`, `ui/` (Compose screens).
  Only included in the build where an Android SDK is installed.

Status: version 1 is feature-complete and ready for the restaurant test. Screens: Setup, PIN
sign-in, New order (dish sheet with modifications), Orders (detail, reprint, change → CHANGED,
cancel), Menu + Modifier lists editing, Staff, Settings (printer test ticket, export).
Not built yet: kitchen screen (needs a second device), payments. Next: the open stories in
`docs/backlog.md`, P0 first.
- Storage: Room; the menu is one JSON document (`MenuEntity`), orders keep JSON snapshots of
  their lines, every ticket is a `print_jobs` row saved before it is sent.
- Printing runs in `AppContainer.appScope` so a ticket still goes out if the screen closes.
- Android 17 needs the runtime `ACCESS_LOCAL_NETWORK` permission ("nearby devices") before the
  app can reach the printer; `ui/LocalNetwork.kt` asks for it.
- Tests: `gradlew :core:test :app:testDebugUnitTest` (Robolectric, in-memory Room, a fake
  printer); keep adding them next to `OrdersTest.kt` / `MenuEditingTest.kt`.

## Cloud frontend (`apps/frontend`)

The design reference and a clickable demo for every screen. It runs on mock data in the browser
and is not used in the restaurant. Stack: React + TypeScript + Vite. Demo logins are on the
sign-in screen.
- `src/domain/` – data model (`types.ts`, the API contract), pricing, modifier rules
  (`modifiers.ts`), order line building (`lines.ts`), ticket layout (`ticket.ts`), role
  permissions. Pure code meant to be shared with the backend.
- `src/data/api.ts` – the `Api` interface; `mockApi.ts` implements it in the browser and
  enforces sign-in, restaurant scoping and roles; `seed.ts` demo data (menu from
  `apps/server/src/menu-data.ts`); `session.tsx` signed-in user and current restaurant.
- `src/screens/` – New order, Orders, order detail, Kitchen, Menu, Modifier lists, Staff,
  Settings, sign-in, restaurant picker, PIN switch. `src/components/` shared pieces.
- Modifications are Toast-style: shared modifier lists attached to categories or dishes; the
  cashier picks NO / ADD / EXTRA / LIGHT / ON SIDE / SUB, then the ingredient. ADD, EXTRA and SUB
  charge the modifier's price.
- Roles: cashier takes orders and marks dishes sold out; manager also edits the menu and manages
  cashiers; owner also manages everyone and settings. A shared tablet switches staff by PIN.

## Local version (`apps/server`, `apps/web`)

The earlier local version: the server runs on a computer in the restaurant, stores data in
SQLite and prints directly over the network. Superseded by the Android app; kept for reference.

## Layout

- `apps/android` – the Android app (see above).
- `apps/frontend` – the cloud frontend, design reference and demo (see above).
- `apps/server` – Node.js + TypeScript backend (Fastify). Runs on the hub (local version).
  - `src/app.ts` routes, `src/orders.ts` order logic, `src/menu.ts` menu,
    `src/ticket.ts` ticket layout + ESC/POS bytes, `src/printer.ts` network/console printers,
    `src/db.ts` SQLite schema (built-in `node:sqlite`, no native modules),
    `src/menu-data.ts` starter menu (seeded into an empty database only), `src/settings.ts`
    restaurant settings (name, tax rate, printer) stored in the database.
- `apps/web` – React + TypeScript tablet app (Vite), installable as a PWA.
- `shared/types.ts` – types used by both sides.

## Commands

- `npm install` – install everything (npm workspaces)
- `npm run dev` – server on :3000 and web app on :5173 (`--host`, so the iPad can open it)
- `npm run dev:frontend` – cloud frontend on :5174 (`--host`); needs no server
- `npm test` – server and frontend tests (Vitest)
- `npm run typecheck` – all apps
- In `apps/android`: `gradlew :core:test` (core tests, needs only JDK 17);
  `gradlew :core:printTest --args="<printer ip>"` sends sample tickets to the real printer
  (add `--chinese` to try Chinese characters)
- `npm run build && npm start` – production: the server also serves the built web app on :3000

## Conventions

- Money is integer cents. Order numbers restart each business day.
- Menu items keep the paper menu's number (`code`, e.g. "L6", "19"). Sizes (Pt/Qt) and protein
  picks ("Chicken or Roast Pork") are option groups; the order must pick one option per group.
- No migrations yet: a database with an older `user_version` is rebuilt on start. Replace this
  with real migrations before the restaurant has live data.
- An order is always saved even if printing fails; the API returns `print.status` and the
  cashier can reprint. Never lose an order because of the printer.
- No printer configured (`PRINTER_HOST` empty) prints tickets to the server log.
- Nothing restaurant-specific in code: menu, prices, tax and printer live in the database and
  are edited in the app (Menu and Settings tabs). The product is meant to be sold to many
  restaurants, so new per-restaurant values go in settings, not constants or env vars.
- Node 22.13+ is required (`node:sqlite`).
